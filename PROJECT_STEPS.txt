# Project steps

A step-by-step record of how this project was built, and the steps still to do.
Each step lists what was done, where it lives, and how to check it.

For the full design (architecture, models, tests), see README.md.
For what is still missing and how to add it, see IMPROVEMENTS.txt.

---

## Setup: environment

**Goal:** a reproducible Python environment with dbt and code quality tools.

1. Dependencies are declared in `pyproject.toml` and pinned in `uv.lock`.
2. The virtual environment lives in `deenv/` (not committed).
3. Python 3.11 is pinned in `.python-version`.
4. Linters: ruff, flake8 and black. Their settings are in `pyproject.toml` and `.flake8`.
   Pre-commit hooks (`.pre-commit-config.yaml`) run the same checks before every commit.

```bash
make install   # uv sync --locked, into ./deenv
make hooks     # install the pre-commit hooks (once)
make lint      # ruff, black, flake8 and file hygiene
```

## Step 1: Generate raw source data ✅

**Goal:** realistic source extracts with change history, so the models have to handle real-world problems.

1. `scripts/generate_raw_data.py` writes four CSVs to `data/raw/`: customers, products, orders and subscriptions.
2. Each file is an append-only extract. Every change is a new row with `updated_at`, `_op` (I/U/D) and `_loaded_at`.
3. The data includes updates, corrections, late-arriving rows, duplicates, hard deletes and messy values.
4. The output is reproducible: the same `--seed` always gives the same files.
5. The logic lives in `scripts/raw_data/`: `history.py` holds the CDC mechanics shared by
   every table, then one module per table and a CSV writer.
6. `scripts/tests/` mirrors that layout with pytest tests, including a fingerprint test that
   fails if the generated data ever changes by accident.

```bash
make data      # defaults: 1000 customers, 6000 orders
make test      # generator tests
```

**Check:** four CSVs in `data/raw/`, and `make test` passes.

## Step 2: Medallion architecture ✅

**Goal:** split the dbt project into Bronze, Silver and Gold layers.

1. **Sources:** `models/staging/_sources.yml` reads the append-only `raw.*` tables (Step 7), all columns as text.
2. **Bronze** (`models/staging`, schema `bronze`, views):
   - `stg_customers`, `stg_products`, `stg_orders`, `stg_subscriptions`
   - Cast types, trim text, turn blanks into nulls, lowercase emails, standardize phones, flag deletes.
   - Deduplicate to one row per (key, `updated_at`), keeping the row loaded last. This removes duplicate deliveries and applies same-timestamp corrections.
3. **Silver** (`models/intermediate`, schema `silver`, tables):
   - SCD Type 2 history for customers, products and subscriptions, built by the `scd2_from_history` macro.
   - `int_orders`: one row per order with lifecycle timestamps.
   - `int_orders_enriched`: orders joined to the customer and product versions valid when the order was placed.
4. **Gold** (`models/marts`, schema `gold`, tables): star schema (Step 4).
5. `macros/generate_schema_name.sql` makes the schemas exactly `bronze`, `silver` and `gold`.
6. `profiles.yml` in the project root points dbt at the local `ecom.duckdb`.

```bash
dbt build
```

**Check:** `dbt build` finishes with no errors, and `ecom.duckdb` has `bronze`, `silver` and `gold` schemas.

## Step 3: Slowly Changing Dimension Type 2 ✅

**Goal:** keep every version of a customer, so past orders show the profile the customer had at the time.

1. Built with custom SQL from the source change log, not with dbt snapshots. The extracts already contain every change with its timestamp. Snapshots only see the state at each dbt run.
2. `macros/scd2_from_history.sql`:
   1. Hashes the tracked columns.
   2. Drops rows where nothing tracked changed.
   3. Sets `valid_from_timestamp` / `valid_to_timestamp` with `lead()`.
   4. Adds `is_current`, `version_number` and `deleted_at`.
3. **Subscription tier** lives in a different source table, so:
   - `int_customer_tier_history` builds the tier timeline (`none`, `basic`, `plus`, `premium`).
   - `int_customer_changes` merges the profile and tier timelines using DuckDB `ASOF JOIN`s.
   - `int_customers_history` turns the merged stream into versions.
4. `dim_customer` exposes the versions. `fact_orders.customer_sk` points to the version valid at order time.
5. `analyses/customer_profile_at_order_vs_today.sql` measures the impact: 1,671 of 5,998 orders (28%) would show the wrong segment, tier, state or email if the customer row were simply overwritten.

```sql
-- A customer's profile at any point in time
select * from gold.dim_customer
where customer_id = 'C00063'
  and timestamp '2025-06-01' >= valid_from_timestamp
  and (timestamp '2025-06-01' < valid_to_timestamp or valid_to_timestamp is null);
```

**Check:** `select * from gold.dim_customer where customer_id = 'C00063' order by version_number` shows 7 versions.

## Step 4: Kimball star schema ✅

**Goal:** Gold layer as a star schema with clearly declared grains.

1. **`dim_date`**: one row per day, with:
   - calendar columns
   - a fiscal calendar (`fiscal_year_start_month`, default February)
   - the 11 US federal holidays, plus the weekday they're observed on when they fall on a weekend
   - Black Friday and Cyber Monday
   - rolling-window flags (last 7/30/90/365 days, month-to-date, year-to-date, fiscal year-to-date) relative to `as_of_date`
2. **`dim_product`**: SCD2, plus product line, style, type, color, price band, launch date and discontinued date.
3. **`dim_customer`**: SCD2 (Step 3).
4. **`fact_orders`**:
   - Grain: one row per order line.
   - Additive measures: quantity, gross revenue, discount, net revenue, cancelled revenue, returned revenue, recognized revenue.
   - Keys to customer, product, and three date roles (order, ship, delivery).
5. **`fact_subscriptions`**:
   - One row per MRR movement or churn event.
   - Movement types: new, expansion, contraction, pause, resume, reactivation, churn.
6. **`fact_subscription_mrr_monthly`**: periodic snapshot of MRR per subscription per month.
7. The README has a bus matrix and an entity diagram.

```sql
-- Monthly MRR bridge
select d.year_month, f.movement_type, sum(f.mrr_change)
from gold.fact_subscriptions f
join gold.dim_date d on d.date_key = f.event_date_key
group by all order by all;
```

**Check:** the MRR movements sum to the snapshot's MRR in every month (October 2026: $4,162.00). A test enforces this.

## Step 5: Tests and documentation ✅

**Goal:** show production-grade data quality and documentation.

1. **Built-in tests:** `unique`, `not_null`, `accepted_values`, `relationships`. Every fact key is checked against its dimension.
2. **Custom generic tests** (`tests/generic/`):
   - `not_negative`: order totals, revenue, quantities, prices and MRR never drop below zero.
   - `scd2_valid_ranges`: validity ranges never overlap and have no gaps, only the last version is current, and deleted records close at the delete.
   - `expression_is_true`: rules across columns, e.g. gross − discount = net.
   - `unique_combination_of_columns`: composite keys and fact grain.
3. **Singular tests** (`tests/`): point-in-time joins, order totals, MRR reconciliation, holidays.
4. **Unit tests** (`models/marts/_unit_tests.yml`): MRR movement classification and order lifecycle roll-up.
5. **Source tests and freshness:** raw keys, `_op` values, and `_loaded_at` age.
6. **Severity:** delivered orders whose ship event arrived late only warn (`is_missing_ship_event`).
7. **Stored failures:** failing rows are saved as views in the `test_failures` schema.
8. **Documentation:**
   - every model described
   - all 161 Gold columns described
   - shared definitions as doc blocks in `models/docs.md`, which also holds the docs home page
9. **Docs site:** published from CI to https://armandpl1.github.io/ecom-data-modeling-project/ (Step 6).

```bash
dbt build                           # 16 models, 145 data tests, 2 unit tests
dbt test --select test_type:unit
dbt source freshness                # reports stale on the static sample data
dbt docs generate && dbt docs serve # lineage graph at http://localhost:8080
```

**Check:** `dbt build` reports 0 errors and 1 warning (the 3 late ship events).

## Step 6: CI/CD ✅

**Goal:** every change is checked automatically, and the docs site deploys itself.

1. `.github/workflows/ci.yml` runs on every pull request and every push to `main`:
   lint and unit tests in parallel, then the dbt build, then (on `main` only) a deploy
   of the docs site to GitHub Pages.
2. Production practices:
   - actions pinned to commit SHAs
   - read-only default token
   - Python, uv and dependencies pinned
   - timeouts on every job
   - artifacts uploaded for debugging failed runs
3. Dependabot (`.github/dependabot.yml`) opens weekly update PRs for actions and Python packages.
4. `main` is protected by a GitHub ruleset: pull requests required, the checks `Lint`,
   `Unit tests (data generator)` and `dbt build and test` must pass, no force pushes.
5. `make ci` runs the same pipeline locally.

```bash
make ci
```

**Check:** the CI/CD badge at the top of the README is green, and the docs site is live.

## Step 7: Persistent raw layer ✅

**Goal:** keep every load, so extracts can be traced and replayed, and make
loading safe to rerun (gap 1 in IMPROVEMENTS.txt).

1. `scripts/load_raw.py` appends each CSV to `raw.<table>` in `ecom.duckdb`,
   adding `_ingested_at`, `_batch_id` and `_file_name` to every row.
2. Each load is logged in `raw._load_log` with the file's SHA-256; a file
   already logged is skipped. Rows and log entry are one transaction.
3. The dbt sources read the raw tables instead of the CSVs; `_load_log` is a
   source with not-null, unique and accepted-values tests.
4. Two singular tests: `assert_raw_no_extract_loaded_twice` and
   `assert_raw_batches_not_empty` (the logged row count matches what landed).
5. `make load` and a CI step run the loader between generating and building.
6. `scripts/tests/test_load_raw.py`: first load, safe rerun, appended new
   extract, columns matched by name, failed load leaves nothing behind.

**Check:** `make build` twice. The second `load` reports all 4 extracts as
skipped, and `dbt build` passes both times. Gold tables are identical to
building from the CSVs directly (checked: same rows and content).

## Step 8: Orchestration with Dagster ✅

**Goal:** run the pipeline in order on a schedule, with alerts, instead of by
hand (gap 3 in IMPROVEMENTS.txt).

1. `scripts/orchestration/definitions.py` defines the assets: the generator
   (`source_extracts`), the raw layer (one asset per raw table plus
   `_load_log`) and every dbt model (`dagster-dbt`). dbt tests become asset
   checks.
2. The raw assets use the dbt source keys (`raw/<table>`), so lineage runs
   from the files to Gold.
3. `daily_pipeline` job, `daily_pipeline_schedule` (06:00 Toronto, off by
   default) and an `alert_on_failure` sensor that posts to `ALERT_WEBHOOK_URL`.
4. `make pipeline` runs it once; `make orchestrate` opens the UI. CI runs the
   pipeline end to end.
5. `scripts/tests/orchestration/test_definitions.py`: every built dbt model is
   an asset, the lineage, checks, schedule, sensor, a real load plus rerun of
   the raw layer, and the alert webhook.

**Check:** `make pipeline` twice. Both runs succeed; the second reloads
nothing. In `make orchestrate`, the lineage graph shows `source_extracts`
feeding the raw tables, then Bronze, Silver and Gold.

## Step 9: Personal data masking and Gold contracts ✅

**Goal:** keep raw personal data out of Gold, and stop Gold schemas from
changing by accident (gaps 9 and 5 in IMPROVEMENTS.txt).

1. `macros/mask_pii.sql`: email hash and domain, last 4 phone digits,
   initials, first 3 ZIP digits.
2. `dim_customer` exposes only masked columns. Raw values move to
   `restricted.dim_customer_pii` (`models/restricted/`), joined on
   `customer_sk`. PII columns are tagged `meta: {pii: true}`.
3. Tests: `assert_no_raw_pii_in_gold` (no raw personal-data column in any
   Gold table) and `assert_dim_customer_pii_is_masked` (masked values only).
4. Every Gold model has `contract: {enforced: true}` and a data type on each
   of its 158 columns.
5. The SCD2 analysis compares `email_hash` instead of `email`; its results
   are unchanged (211 email changes, 1,671 orders affected, 28%).

**Check:** `dbt build` passes (177 nodes, the one known warning). Add a Gold
table with an `email` column: the build fails. Change a Gold column's type:
the build fails with a contract error.

## Step 10: Incremental models ✅

**Goal:** process only what changed on each run, and prove the result is the
same as a full rebuild (gap 2 in IMPROVEMENTS.txt).

1. Bronze (`stg_*`): incremental on the raw layer's `_ingested_at`; existing
   rows for the same key and `updated_at` compete with new ones, so the row
   loaded last still wins. `batch_id` and `ingested_at` are kept on each row.
2. Silver SCD2 histories and `int_orders`: per-entity rebuild of entities
   with Bronze rows newer than the table's `_max_ingested_at` watermark
   (`scd2_from_history` gained an optional `where` filter).
3. Gold `fact_orders` and `fact_subscriptions`: delete+insert per order and
   per subscription for inputs ingested in the latest load round or
   `incremental_lookback_hours` before it (`macros/incremental_window_start.sql`).
4. `scripts/check_incremental.py` (`make check-incremental`, in CI): two
   simulated nightly loads, incremental vs full refresh, every Gold and
   restricted table compared. `ECOM_DUCKDB_PATH` in profiles.yml lets it
   build into separate files.
5. The two unit tests declare `is_incremental: false` (they test the full
   computation).

**Check:** `make check-incremental` prints `OK: 7 tables identical`.
Measured: batch 2 read exactly its 2,070 raw rows, rebuilt 111 customers,
4 products, 31 subscriptions and 792 orders in Silver, and a rerun with no
new load read 0 rows. On this small dataset the incremental run is slower
than a full refresh (74.7 s vs 45.6 s on a laptop).

## Step 12: Semantic layer and dashboard ✅

**Goal:** define business metrics once and serve them to a dashboard (gap 7
in IMPROVEMENTS.txt).

1. MetricFlow semantic models on fact_orders, fact_subscriptions and
   fact_subscription_mrr_monthly (`models/semantic/`), with dim_date as the
   time spine. dbt-metricflow 0.16.0 works with dbt-core 1.12.7.
2. Metrics: recognized revenue, orders, average order value, MRR, paying
   subscriptions, net new MRR, churned subscriptions, churn rate (against the
   start of the month), trial conversions and trial conversion rate.
3. `scripts/export_metrics.py` (`make metrics`, in CI): `mf validate-configs`,
   then `mf query` per dataset to CSV.
4. `dashboard/`: Evidence (npm packages) reads the CSVs; `make dashboard`
   builds a static site. The dashboard is a dbt exposure.

**Check:** `make metrics` reports 0 validation errors and writes 34, 34 and
12 rows. `uv run mf query --metrics mrr --group-by metric_time__month` gives
4,162 for 2026-10. `make dashboard` builds; the page shows MRR $4,162.
